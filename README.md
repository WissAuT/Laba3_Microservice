## Шаг 1. Анализ предметной области

### 1.1. Описание системы
Система предназначена для автоматизации работы ипподромного тотализатора. Она позволяет зрителям и зарегистрированным игрокам просматривать расписание заездов, актуальные коэффициенты на лошадей, пополнять свой игровой баланс, делать ставки на победу в заездах, а также автоматически получать выплаты при выигрыше. Администрация ипподрома использует систему для формирования расписания заездов, регистрации лошадей и вноса официальных результатов испытаний.

### 1.2. Акторы
* **Игрок (Клиент):** Просматривает заезды, пополняет баланс, делает ставки, отслеживает их статус и историю выплат.
* **Судья / Администратор:** Формирует расписание заездов, управляет списком участников, заносит официальные результаты завершившихся скачек.
* **Платёжный шлюз (Внешняя система):** Внешний сервисный провайдер для проведения банковских транзакций по пополнению кошелька игрока.

### 1.3. Пользовательские сценарии
1. **Как игрок**, я хочу просматривать список предстоящих заездов и участников, чтобы выбрать подходящее событие для ставки.
2. **Как игрок**, я хочу пополнять свой внутренний кошелек с банковской карты, чтобы совершать ставки.
3. **Как игрок**, я хочу делать ставку на конкретную лошадь до начала заезда, чтобы участвовать в тотализаторе.
4. **Как игрок**, я хочу отменять свою ставку до закрытия приема ставок, чтобы вернуть средства при изменении решения.
5. **Как судья**, я хочу регистрировать заезды и привязывать к ним лошадей-участников.
6. **Как судья**, я хочу зафиксировать официальные результаты заезда (победителя), чтобы система рассчитала ставки.
7. **Как игрок**, я хочу получать пуш-уведомление о результатах сделанной ставки и зачислении выигрыша.

### 1.4. Доменные события
* `RaceCreated` — создан новый заезд.
* `RaceStatusChanged` — изменен статус заезда (например, приём ставок закрыт, заезд начался).
* `RaceFinished` — заезд завершен, зафиксирован официальный победитель.
* `BetPlaced` — игрок сделал новую ставку.
* `BetCancelled` — ставка отменена игроком до начала заезда.
* `PoolRecalculated` — пересчитан общий пул ставок и коэффициенты на участников.
* `BetCalculated` — ставка рассчитана (статус: Выиграла / Проиграла).
* `PayoutProcessed` — выигрыш зачислен на баланс игрока.

### 1.5. Ограниченные контексты (Bounded Contexts) и глоссарии

#### Контекст «Заезды и Каталог» (`race-context`)
* **Заезд (Race):** спортивное состязание лошадей с определенным временем старта и дистанцией.
* **Лошадь (Horse):** животное-участник состязания с уникальным регистрационным номером.
* **Жокей (Jockey):** спортсмен, управляющий лошадью в конкретном заезде.

#### Контекст «Приём Ставок» (`betting-context`)
* **Ставка (Bet):** зафиксированное соглашение игрока поставленной суммы на конкретный исход заезда.
* **Идемпотентность ставки:** уникальный ключ запроса, предотвращающий повторное списание при сбое сети.

#### Контекст «Тотализатор и Пул» (`totalizator-context`)
* **Пул ставок (Bet Pool):** общая сумма денежных средств, поставленная всеми игроками на конкретный заезд.
* **Коэффициент (Odds):** динамический множитель выигрыша, рассчитываемый на основе доли ставок на данную лошадь относительно общего пула.

#### Контекст «Финансы и Выплаты» (`payout-context`)
* **Кошелек (Wallet):** внутренний счет пользователя в системе тотализатора.
* **Холдирование (Hold):** временная задержка/заморозка средств на кошельке до подтверждения валидности ставки.
* **Выплата (Payout):** транзакция перевода денежных средств со счета тотализатора на кошелек игрока по выигравшей ставке.

#### Контекст «Уведомления» (`notification-context`)
* **Уведомление (Notification):** асинхронное текстовое сообщение (Email/Push/SMS), отправляемое пользователю при изменении статусов его ставок.

## Шаг 2. Список и описание сервисов

В системе выделено 5 бизнес-сервисов (не считая API Gateway и Keycloak):

### 1. `race-service`
* **Ответственность:** Управление расписанием заездов, карточками лошадей и жокеев.
* **Владеет данными:** `Race`, `Horse`, `Jockey`.
* **Предоставляет:** `GET /api/v1/races`, `POST /api/v1/races`, `GET /internal/v1/races/{id}`.
* **Зависит от:** Автономен.
* **Нефункциональные требования:** Высокая частота чтения (RPS чтения в 50 раз выше записи).
* **Обоснование границы:** Изолирует справочную информацию о заездах. Изменения в структуре каталога не затрагивают логику проведения платежей или пересчета пула.

### 2. `betting-service`
* **Ответственность:** Валидация и регистрация ставок клиентов, поддержка отмены ставок.
* **Владеет данными:** `Bet`.
* **Предоставляет:** `POST /api/v1/bets`, `POST /api/v1/bets/{id}/cancel`, `GET /api/v1/bets/my`.
* **Зависит от:** `race-service` (проверка статуса заезда), `payout-service` (холдирование средств), RabbitMQ (публикация события `BetPlaced`).
* **Нефункциональные требования:** Высокая критичность к задержкам (<100мс) и поддержка идемпотентности.
* **Обоснование границы:** Ядро взаимодействия с игроками. Высокая нагрузка перед самым стартом заезда.

### 3. `totalizator-service`
* **Ответственность:** Накопление пула ставок, пересчет текущих коэффициентов, расчет результатов выигрышей после завершения заезда.
* **Владеет данными:** `BetPool`, `CalculatedOutcome`.
* **Предоставляет:** `GET /api/v1/pools/{raceId}`, `POST /internal/v1/results`.
* **Зависит от:** RabbitMQ (подписка на `BetPlaced`, `RaceFinished`), публикует `BetCalculated`.
* **Нефункциональные требования:** Очередь событий должна гарантировать обработку без потерь (At-Least-Once).
* **Обоснование границы:** Сложная математика расчёта пропорций тотализатора изолирована в отдельном сервисе и не замедляет приём ставок.

### 4. `payout-service`
* **Ответственность:** Ведение кошельков пользователей, заморозка (hold), списание и зачисление выигрышей.
* **Владеет данными:** `Wallet`, `FinancialTransaction`.
* **Предоставляет:** `GET /api/v1/wallets/me`, `POST /internal/v1/wallets/hold`, `POST /internal/v1/wallets/release`.
* **Зависит от:** RabbitMQ (подписка на `BetCalculated`), внешний платёжный шлюз.
* **Нефункциональные требования:** Строгая финансовая транзакционность (ACID).
* **Обоснование границы:** Финансовый контур требует строгого аудита и ограниченного доступа.

### 5. `notification-service`
* **Ответственность:** Формирование и отправка пуш-уведомлений и Email по событиям в системе.
* **Владеет данными:** `NotificationTemplate`, `NotificationLog`.
* **Предоставляет:** Внутренние обработчики очередей RabbitMQ.
* **Зависит от:** RabbitMQ (подписка на `BetPlaced`, `BetWon`, `PayoutProcessed`).
* **Нефункциональные требования:** Eventual consistency, сбой сервиса не должен влиять на расчеты выигрышей.
* **Обоснование границы:** Фоновый асинхронный сервис с некритичными требованиями к сбоям.

### Отвергнутый вариант разбиения
Рассматривалось объединение `betting-service` и `totalizator-service` в один сервис. От этого отказались: перед началом заезда поток ставок (`betting-service`) огромный, а пересчет математического пула и коэффициентов (`totalizator-service`) требует ресурсов процессора. Их разделение позволяет масштабировать приём ставок независимо от сервиса расчёта коэффициентов.

## Шаг 3. Выбор готового ПО

| Компонент | Кто использует | Обоснование |
| :--- | :--- | :--- |
| **PostgreSQL** (отдельная БД у каждого) | `race-service`, `betting-service`, `payout-service` | Строгая транзакционность (ACID), необходимость реляционных связей между финансовыми операциями и ставками. |
| **MongoDB** | `totalizator-service`, `notification-service` | Гибкая документная схема для хранения снимков пула с разным набором участников и истории логов уведомлений. |
| **Redis** | `race-service` | Кэширование активных заездов и коэффициентов для снижения нагрузки на PostgreSQL при массовом чтении пользователями. |
| **RabbitMQ** | Все сервисы | Гарантированная доставка сообщений, подписка нескольких сервисов на одни и те же события (pub/sub), поддержка DLQ. |
| **Spring Cloud Gateway** | Вход для всех клиентов | Единый API Gateway: маршрутизация, проверка JWT-токенов, ограничение rate limiting. |
| **Keycloak** | API Gateway | Готовая OpenID Connect / OAuth2 система для аутентификации пользователей и администраторов. |

| :-: | :--- | :-: | :--- | :--- |
| 1 | Клиент → Gateway → `race-service` | sync | `GET /api/v1/races` | Просмотр активных заездов |
| 2 | Клиент → Gateway → `betting-service` | sync | `POST /api/v1/bets` | Создание новой ставки |
| 3 | `betting-service` → `race-service` | sync | `GET /internal/v1/races/{id}` | Проверка: заезд существует и приём ставок открыт |
| 4 | `betting-service` → `payout-service` | sync | `POST /internal/v1/wallets/hold` | Холдирование (заморозка) суммы ставки на балансе |
| 5 | `betting-service` → RabbitMQ | async | Exchange: `bet.events` / Key: `bet.placed` | Публикация события о принятой ставке |
| 6 | `totalizator-service` (из RabbitMQ) | async | Queue: `tot.bet-placed` | Приём события ставки, пересчет пула заезда |
| 7 | `race-service` → RabbitMQ | async | Exchange: `race.events` / Key: `race.finished` | Заезд завершен, зафиксирован победитель |
| 8 | `totalizator-service` (из RabbitMQ) | async | Queue: `tot.race-finished` | Старт расчета всех ставок заезда |
| 9 | `totalizator-service` → RabbitMQ | async | Exchange: `bet.events` / Key: `bet.calculated` | Событие: ставка рассчитана (выигрыш/проигрыш) |
| 10 | `payout-service` (из RabbitMQ) | async | Queue: `payout.bet-calculated` | Начисление выигрыша на кошелек при победе |
| 11 | `notification-service` (из RabbitMQ)| async | Queue: `notif.events` | Отправка пуш-уведомления пользователю |
